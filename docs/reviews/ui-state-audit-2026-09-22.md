## 프로젝트 이해

현재 제품의 중심은 **평가 폴더의 로그에서 근거를 찾고, 판정과 규칙을 확정한 뒤, 결과와 평가 이력을 남기는 로컬 작업 도구**다.

주요 작업은 다음 순서로 이어진다.

`평가 폴더 연결 → 로그 검색 → 근거 확인 → 수동 판정 → 폴더에 규칙 적용 → 예외 검토 → 결과 표·CSV → 평가 이력`

| 영역 | 현재 역할 | 주요 코드 |
|---|---|---|
| 화면 연결 | 프로젝트, 파일, 판정, 결과, Agent 상태 연결 | `src/App.tsx` |
| 로그 작업 | 파일 탭, 검색, 근거, 수동 판정, 규칙 편집·일괄 적용 | `src/views/WorkbenchView.tsx` |
| 결과 | 판정 목록, 조건 수정, 선택 승인, CSV·TSV | `src/views/ResultsView.tsx` |
| 결과 정리 | 축·집계·차트·주소 이벤트 분석 | `src/views/PatternsView.tsx` |
| 평가 이력 | 가설·평가·비교 관계와 근거 기록 | `src/views/EvaluationMemoryView.tsx` |
| 로컬 서비스 | 파일 검색·검사, 프로젝트 및 판정 revision 저장 | `electron/main/artifact-service.ts`, `project-store.ts`, `evaluation-store.ts` |
| Agent | 제한된 근거 조회, 해석과 이력·보기 제안 | `src/components/AgentPanel.tsx`, `electron/main/native-agent-service.ts` |

검색·판정 엔진과 저장소에는 이미 검증, revision 충돌 처리, 요청 세대 검사 등이 있다. 주요 빈틈은 **프로젝트 전환, 규칙 변경, 화면 이동처럼 기능과 기능 사이의 상태 전환**이다. 전면적인 디자인 교체보다 이 경계를 정리하는 편이 효과가 크다.

## 우선 수정할 문제

P1은 결과 신뢰성이나 반복 작업을 직접 방해하는 문제, P2는 작업 효율과 회귀 방지 문제다. ‘실행 재현’은 제품 함수를 테스트 입력으로 실행했다는 뜻이며 실제 사용자 저장소를 변경했다는 뜻이 아니다.

### 1. 적용 완료 후 다음 규칙 작업으로 이어지는 버튼이 사라짐 — P1

**확인 수준:** 브라우저 조작 재현. 버튼 숨김 조건은 현재 로컬 수정에서 추가되었다.

재현:

1. 합성 로그에서 `DDR training`을 검색하고 Enter로 검색을 확정한다.
2. 결과를 Pass로 선택한다.
3. `현재 폴더에 적용`을 누른다.
4. 같은 로그에서 검색어를 `UFS link`로 바꾸고 Enter를 누른다.

실제 결과: `현재 폴더 적용 완료 (2개)`만 남고, 바로 앞에 있던 `현재 폴더에 적용`과 `규칙 편집`이 다시 나타나지 않았다. 규칙 관리 등으로 우회해야 한다.

원인: `WorkbenchView.tsx:3741`에서 `!recipeSaved && batchPreview.status !== 'done'`일 때만 빠른 동작을 렌더링한다. 검색 확정 경로(`:1712`)는 이 완료 상태를 해제하지 않는다.

수정 방향: 적용 버튼의 위치를 유지하고 상태에 따라 `폴더에 적용 / 적용 중 / 다시 적용`으로 바꾼다. 검색 근거나 규칙 조건을 바꾸면 변경 있음 상태가 되어야 한다. 적용 완료는 작은 상태 표시로 남긴다.

완료 기준: 적용 → 검색 변경 → 조건 편집 → 재적용을 화면 이동 없이 끝낼 수 있다. 키보드 포커스도 완료 시 사라지지 않는다.

### 2. 규칙 발생 횟수·순서를 수정해도 다른 폴더의 과거 판정이 유효하게 복원됨 — P1

**확인 수준:** 실제 함수 실행 재현. 원격 `main`에도 같은 ID 기반 복원 로직이 있다.

재현 조건: 같은 규칙을 여러 폴더에 적용한 뒤 한 폴더에서 `1회 이상`을 `정확히 2회`로 수정한다. 아직 재적용하지 않은 다른 폴더의 이전 배치를 복원한다.

실행 결과:

| 검사 | 결과 |
|---|---|
| `PASS`가 한 번 있는 로그를 수정 규칙으로 계산 | `UNKNOWN` |
| 동일 로그의 기존 배치를 `hydrateEvaluation`으로 복원 | `PASS` |
| 현재 규칙의 발생 조건 | `exact: 2` |
| 적용 규칙 복원 함수가 돌려준 발생 조건 | `atLeast: 1` |

원인: `App.tsx:193`, `:232`에서 현재 활성 rule ID의 존재만 비교한다. `WorkbenchView.tsx:2125`의 규칙 생성은 기본 ID를 만든 뒤 발생 횟수와 순서를 덧씌우므로 이 편집에서는 ID가 유지될 수 있다. 폴더별 복원은 과거 배치의 규칙 내용을 가져온다.

수정 방향: `ruleId`와 내용 revision 또는 fingerprint를 함께 비교한다. 영향을 받는 폴더를 `재검사 필요`로 표시하고, 최신 규칙으로 재검사하기 전에는 현재 기준의 확정 판정으로 집계하지 않는다. 과거 실행 결과는 이력으로 보존한다.

완료 기준: A·B 폴더에 적용 → A에서 횟수/순서 수정 → B 열기 → 앱 재시작까지 수행해도 B의 이전 PASS가 최신 판정으로 표시되지 않는다.

### 3. 규칙 삭제 이후에도 이전 ‘규칙 충돌’ 이유가 남음 — P1

**확인 수준:** 실제 함수 실행 재현. 원격 `main` 공통.

규칙을 archive한 snapshot에 기존 `UNKNOWN / RULE_CONFLICT` 배치를 넣으면 복원 결과가 여전히 `ruleNeedsReview: true`, `ruleExceptionCode: RULE_CONFLICT`다.

원인: `App.tsx:212` 부근은 `outcomeSource === 'rule'`인 결과에만 활성 규칙 검사를 한다. `outcomeSource: 'unknown'`인 충돌 배치는 규칙 변경과 무관하게 유지된다. `WorkbenchView.tsx:2077`의 삭제는 연결 규칙을 제거하지만 영향받은 결과 전체의 유효 상태를 다시 계산하지 않는다.

수정 방향: 모든 자동 결과와 예외에 실행 당시 규칙 집합 revision을 연결한다. 삭제 후에는 `이전 규칙 기준 / 재검사 필요`로 전환하거나 남은 규칙으로 다시 계산한다. 근거 없이 다른 과거 PASS를 되살리면 안 된다.

완료 기준: 충돌 규칙 두 개 → 한 개 삭제 → 재계산 → 재시작에서 판정과 검토 이유가 일치한다. 마지막 규칙 삭제도 별도 검증한다.

### 4. ‘폴더에서 규칙 해제’와 ‘수동 판정 취소’가 독립적인 동작으로 제공되지 않음 — P1

**확인 수준:** UI·코드 확인. 기존 기능 경계의 빈틈.

- 규칙 관리에는 현재 폴더에 적용, 규칙 편집, 삭제가 있다. 특정 폴더에서만 적용을 해제하는 동작이 없다(`WorkbenchView.tsx:3818`).
- 수동 판정을 한 번 저장하면 `결과를 선택하세요`로 돌아가는 선택은 처리하지 않는다(`:3719` 부근). `미확인` 선택은 판정 취소가 아니라 `UNKNOWN`이라는 수동 판정을 저장한다.
- `resolvePrecomputedBatch`(`:1248`)는 저장된 수동 판정을 우선 보존한다. 따라서 `미확인`을 골라도 자동 규칙 판정으로 복귀하지 않는다. 계약과 preload에도 판정 reset 동작이 없다.

수정 방향: `이 폴더에서 해제`, `프로젝트 규칙 삭제`, `수동 판정 취소`를 구분한다. 해제/취소도 저장 이력으로 남기고 자동 판정과 예외를 다시 계산한다. 수동 판정을 규칙 해제와 함께 지우면 안 된다.

완료 기준: 수동 PASS → 수동 판정 취소 → 규칙 결과 복귀, 폴더 A 해제 → 폴더 B 적용 유지가 모두 가능하다.

### 5. 프로젝트 전환 중 이전 저장 응답이 현재 프로젝트를 되돌릴 수 있음 — P1

**확인 수준:** 저장 큐 함수 실행으로 늦은 응답의 상태 덮어쓰기를 재현. 실제 IPC·프로젝트 저장소까지 연결한 장애 테스트는 후속 필요. 원격 `main`에도 같은 구조가 있다.

실행: A 프로젝트 저장을 대기시킴 → 현재 프로젝트를 B로 변경 → A 저장 완료. `createLatestProjectSaveQueue`는 현재 B임에도 A의 `onSaved`를 호출했고, 현재 상태가 A로 돌아갔다.

원인:

- `App.tsx:403`의 큐는 시작/완료 시 프로젝트 소유권을 검증하지 않는다.
- 실제 소비 경로 `App.tsx:1026` 부근은 완료 결과를 `projectRef.current`와 `projectUpdated`에 그대로 넣는다.
- `enqueueEvaluation`(`:492`)도 앱 마운트 세대만 검사한다. 프로젝트를 바꾸는 `projectGeneration`과 별개다.
- 표 구성 저장 등의 `onProjectUpdated(next)`에도 현재 프로젝트 ID 검사가 없다.

수정 방향: 작업 생성 때 `{projectId, projectGeneration, operationId}`를 고정한다. 저장은 시작 당시 프로젝트에만 수행하고, 응답 반영은 현재 프로젝트와 세대가 일치할 때만 한다. 대기 큐도 프로젝트별로 나눈다.

완료 기준: 판정 저장·규칙 적용·표 구성 저장·평가 이력 저장을 각각 지연시킨 상태에서 A→B→A로 전환해도 다른 프로젝트의 화면이나 데이터에 섞이지 않는다.

### 6. Agent의 비동기 실패 사유가 화면에 나타나지 않는 경로 — P1

**확인 수준:** 서비스·계약·렌더링 코드 대조. 외부 LLM 장애를 실제로 발생시키지는 않았다. 원격 `main` 공통.

`native-agent-service.ts:548`, `:608`은 실패 내용을 세션의 `failure`에 저장하고 `paused` 업데이트를 보낸다. 반면 `AgentPanel.tsx:1028`은 paused/failed에서 재시도 아이콘만 표시한다. 이 컴포넌트는 `nativeSession.failure`를 읽지 않는다. 별도의 로컬 `error`는 API 호출 자체가 reject되는 경우 등에만 채워진다.

따라서 백그라운드 처리 중 발생한 실패는 이유를 알 수 없고, 로컬 요약이 있으면 LLM 해석도 끝난 것으로 오해할 수 있다.

수정 방향: 실패 상태를 `분석을 완료하지 못했습니다 · 시간 초과`처럼 짧게 표시하고 `재시도`, 필요한 경우 `연결 설정`을 제공한다. 유지된 로컬 결과와 미완료 해석의 상태를 구분한다. 상세 오류는 펼쳐서 본다.

완료 기준: timeout, 429, 연결 실패, 중지, 재시작 후 실패 세션 복원에서 원인과 다음 행동이 보인다.

### 7. 일부 로그 검사 실패가 ‘결과 없음’과 구분되지 않고 캐시됨 — P1

**확인 수준:** 코드 경로 확인. 파일별 오류 주입 E2E는 후속 필요.

`App.tsx:698`, `:736`에서 단계·Fail 주소 검사 결과의 `source.error`를 건너뛰고 성공 부분만 캐시한다. 개별 실패 목록이나 실패 개수는 화면 모델로 전달하지 않는다. 최초 로딩도 빈 결과로 시작한다.

문제: 검사가 아직 안 끝난 상태, 실제 이벤트 0건, 검사 실패가 같은 빈 결과처럼 보일 수 있다. 부분 결과가 캐시에 남으면 화면 왕복만으로 실패 파일을 다시 검사하지 못한다.

수정 방향: 검사 상태를 `loading / complete / partial / error`로 모델링한다. `100개 중 3개 검사 실패 · 다시 검사`를 표시하고, 불완전한 집계와 내보내기에 범위를 명시한다. 실패 파일은 재시도 가능해야 한다.

완료 기준: 100개 중 1개 권한 오류, 파일 누락, 중간 검사 실패에서 전체 정상 0건으로 표시하지 않는다.

### 8. 저장·캐시·적용이 분리되어 중간 실패와 중복 클릭을 일관되게 다루기 어려움 — P1

**확인 수준:** 코드 확인. localStorage 용량 초과·디스크 장애·연속 클릭의 실제 주입 테스트는 후속 필요.

- `WorkbenchView.tsx:3302`부터 서버 규칙 저장 → localStorage 저장 → 규칙 적용을 진행한다. 서버 저장 후 localStorage가 실패하면 규칙은 존재하지만 전체 저장 실패 메시지가 나온다.
- 저장 요청을 보내는 순간의 별도 saving lock이 없으며, 적용 running 상태는 나중에 설정한다. 느린 저장 응답 중 중복 실행을 막는 경계가 약하다.
- `PatternsView.tsx:419`, `ResultsView.tsx:290`은 보기/열 preset 저장 후 관련 Harness preset을 다시 저장한다. 두 번째 저장 실패 시 부분 성공 상태가 남는다.

수정 방향: 영속 저장의 기준을 정하고 renderer 캐시 실패가 본 저장 성공을 뒤집지 않게 한다. 필요한 두 preset은 하나의 서비스 트랜잭션으로 저장한다. 동작 시작부터 lock을 잡고 재시도 시 같은 operation ID를 쓴다. 부분 성공 시 완료된 단계와 재시도할 단계를 정확히 표시한다.

### 9. 지원하는 최소 창 크기에서도 검색·하단 버튼이 잘림 — P2

**확인 수준:** 브라우저 조작·화면 확인.

Electron 최소 창은 `electron/main/index.ts:39`의 1100×680이다. 동일 크기에서 기본 좌우 패널을 유지하면 검색창의 오른쪽 이동/닫기 도구가 편집기 경계를 넘어가고, 하단 `전체 프로젝트` 찾기 버튼도 잘린다. 1280×720에서도 하단 도구의 마지막 항목이 잘리는 것을 확인했다.

원인: 검색창의 고정 폭 요소 합계(`workbench.css:249`, `:289`부터)와 줄바꿈 없는 하단 버튼(`:381`)이 남은 편집기 폭보다 크다. breakpoint는 주로 단축키 글자를 숨길 뿐이다.

수정 방향: 찾기는 하나의 입력과 범위 선택으로 통합한다. 줄 이동·줄바꿈 등 보조 기능은 더보기로 옮기거나 공간에 맞게 배치한다. 검색 닫기, 판정, 적용, 중지는 창 크기나 패널 폭과 무관하게 접근 가능해야 한다.

완료 기준: 1100×680, 1280×720, 1480×940에서 좌우 패널 최소/최대, 긴 파일명, Agent 열림을 교차 검사한다. 화면 배율 확대도 확인한다.

### 10. 화면 이동으로 미저장 표 구성이 사라짐 — P2

**확인 수준:** 브라우저에서 Skew 축 제거 → 결과 이동 → 결과 정리 복귀 시 원래 축으로 복원되는 것을 재현. 브라우저는 구성 저장이 비활성이라는 제한이 있다. Electron도 화면을 unmount하고 저장 preset으로 초기화하는 구조라 미저장 초안 보존이 없다.

`App.tsx:1078` 이하에서 페이지별 컴포넌트를 교체한다. `PatternsView.tsx:393`은 폴더 또는 `project.exportPresets` 갱신 때 저장값으로 모든 조작 상태를 덮어쓴다. 결과 화면의 열 선택도 유사하다(`ResultsView.tsx:157`).

수정 방향: 폴더별 현재 작업 초안과 다음 실행의 기본 구성을 구분해 저장한다. 화면 왕복은 초안을 보존한다. 관련 없는 프로젝트 변경이 dirty 상태의 표를 초기화하지 않도록 한다. 매번 경고창을 띄우기보다 자동 초안 보존이 적합하다.

### 11. 실제 상태 전환을 검증하는 테스트 보강이 필요 — P2

현재 `WorkbenchView.tsx`는 3,834줄, `App.tsx`는 1,166줄, `AgentPanel.tsx`는 1,040줄이다. 파일 길이 자체가 버그는 아니지만 저장·화면·검색·규칙의 상태 조합을 개별 boolean으로 관리하는 비용이 크다.

`tests/renderer/workbench-view.test.ts`, `ui-readability-contract.test.ts` 등은 유용한 함수 검사와 함께 소스 문자열/CSS 존재 검사도 많이 사용한다. 이를 통과해도 버튼이 실제로 눌리는지, 재진입 후 결과가 맞는지는 보장되지 않는다.

수정 방향: 엔진 단위 테스트를 유지하고 아래 시나리오를 실제 컴포넌트/브라우저 및 Electron 통합 테스트에 추가한다. 이번 문구 실패 두 건도 제품 계약에 맞춰 정리한다.

## 행동 중심 UI 정리안

### 공통 원칙

1. 버튼은 행동을 이름으로 쓴다: `적용`, `다시 검사`, `판정 취소`, `표 복사`, `CSV 저장`.
2. 필수 동작의 위치는 고정한다. 상태가 바뀌면 문구·활성 여부를 바꾸고 동작 자체를 없애지 않는다.
3. 숨김과 비활성을 구분한다. 지금 실행할 수 없는 핵심 동작은 짧은 이유를 붙여 비활성으로 유지한다.
4. 설명은 선택과 행동에 도움이 될 때만 표시한다. 일반 상태에서는 장문 도움말, 반복 배지, 추천 문구를 줄인다.
5. 오류는 한 줄 원인과 복구 동작으로 표시한다. 현재 3.2초 toast(`App.tsx:632`)만으로 중요한 저장 실패를 처리하지 않는다.
6. 원본 로그 읽기 전용, 판정 근거 추적, 엔지니어 확인 이력은 유지한다.

### 화면별 기본 동작

| 화면 | 먼저 보여줄 것 | 필요할 때 펼칠 것 |
|---|---|---|
| 로그 | 폴더·로그, 검색, 판정 선택, 폴더에 적용, 다음 확인 대상 | 정규식·발생 횟수·순서, 규칙 상세, 검색 고급 옵션 |
| 결과 | 현재 폴더, 확인 필요 필터, 결과 표, 내보내기 | 단계별 필터, 열 선택, 근거 열, 일괄 추출값 승인 |
| 결과 정리 | 현재 폴더, 판정/불량률 등 대표 보기, 표·차트, 복사·저장 | 축 편집, 세부 집계, 주소 이벤트, 고급 필터 |
| 평가 이력 | 평가 선택, 이전 평가와 비교, 해석 수정, 이력 저장 | 관계·가설 상세, 내부 출처 정보 |
| Agent | 현재 분석 범위, 질문 입력, 진행/중지, 답변·근거 | 추천 질문, 도구 실행 과정, 보기 제안의 상세 설명 |

Agent 기능을 제거할 이유는 없다. 여러 화면에 흩어진 Sparkles 버튼과 추천·설명 UI를 기본 작업과 경쟁시키지 않고, 현재 선택 범위에 대한 한 가지 분석 진입점으로 모으는 것이 목표다. `현재 표 분석`처럼 실제 행동은 유지하되 중복 진입점은 줄인다.

규칙 관리에서는 **규칙 자체의 저장 상태**와 **각 폴더에 적용된 상태**를 별도로 보여줘야 한다. `저장됨`, `현재 폴더 적용됨`, `수정 후 재검사 필요`는 서로 다른 상태다.

## 권장 구현 순서

### 1차: 결과와 저장의 신뢰성

- 프로젝트별 저장 큐와 응답 반영 검사.
- 규칙 revision/내용과 배치 결과 유효성 연결.
- 폴더 적용 해제, 수동 판정 취소의 계약·저장·UI 연결.
- 부분 검사 실패와 Agent 비동기 실패의 가시화.
- 저장 중복 방지와 부분 성공 처리.

### 2차: 로그 작업 흐름 정리

- 적용·재적용·판정 취소·다음 예외 버튼의 위치 고정.
- `editing / saving / applying / applied / stale / error` 등 명시적인 상태 전환으로 정리.
- 지원 최소 폭에서 검색·패널·하단 도구의 잘림 제거.
- 화면 왕복과 파일 전환에 대한 작업 초안 보존.

### 3차: 결과와 Agent의 기본 화면 단순화

- 결과의 중복 필터와 내보내기 동작 정리.
- 결과 정리의 축·집계 설정을 한 곳에 모으고 데이터 영역 확보.
- Agent 추천·설명·실행 상세를 필요 시 펼치는 구성으로 정리.
- 동작 변경에 맞춰 현재 한국어 매뉴얼 갱신.

각 단계는 변경된 상태 전환 테스트를 먼저 통과시킨 뒤 다음 화면으로 확장한다. 큰 파일을 먼저 전부 분리하는 리팩터링보다 재현 가능한 문제 단위로 상태 소유권을 옮기는 편이 검증하기 쉽다.

| 저장 버튼 연속 클릭 / 재시도 | 논리적 작업 한 번만 저장·적용 |
| 서버 저장 성공 후 renderer 캐시 실패 | 성공한 저장을 전체 실패로 표시하지 않음 |

| 일부 파일 누락·권한 없음·검사 오류 | 성공 범위와 실패 범위 구분, 실패 항목 재검사 가능 |

| 표 편집 후 다른 화면 이동·복귀 | 현재 폴더의 작업 초안 유지 |
