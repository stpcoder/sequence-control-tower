# 실장 엔지니어 사용 시나리오

이 문서는 현재 `로그`, `결과표`, `설정` 화면으로 합성 SoC 로그를 검증하는 세 가지 작업을 설명합니다. 예시는 `tests/fixtures/engineer-workflow/`의 48개 로그와 `tests/fixtures/qualcomm-bringup/`의 160개 로그를 기준으로 합니다. Qualcomm fixture의 `SYN_*` 단계 표기는 테스트용 합성 문자열입니다.

모든 작업에서 원본 로그 파일은 읽기 전용으로 열립니다. 원문 편집기에서 내용, 공백, 줄 번호를 수정하지 않으며 근거 선택은 분석 상태에만 저장됩니다.

## 1. 검증 엔지니어: 여러 폴더 분류

### 입력과 목표

`engineer-workflow` fixture는 다음 조합으로 구성됩니다.

| 축 | 값 |
| --- | --- |
| Sample | `SAMP-A` ~ `SAMP-D` |
| 온도 | `-40C`, `25C`, `85C` |
| Mode | `DIAG`, `STRESS` |
| 실행 | `RUN=1`, `RUN=2` |

총 48개 파일을 여러 폴더에 두고 같은 검색 근거와 판정 규칙을 반복 적용합니다. 파일명과 폴더의 상대 경로를 유지하면서 `PASS`, `DIAG_FAIL`, `TEST_FAIL`, `TRAINING_FAIL`, `SYSTEM_HALT`, `SYSTEM_REBOOT`, `INCOMPLETE`, `UNKNOWN`을 분류하는 작업입니다.

### 작업 순서

1. `로그` 화면에서 `로그 폴더 열기`를 누릅니다. Windows는 `Ctrl+O`, macOS는 `⌘O`를 사용할 수 있습니다. 선택 폴더가 여러 개면 한 번에 선택하고, 선택 창이 한 폴더만 허용하면 `로그 폴더 열기`를 반복합니다.
2. 가져오기 완료 알림의 등록 수, `실패` 수, `제외` 수를 확인합니다. 같은 이름의 루트가 있으면 목록과 `결과표`에서 안정적인 root ID 순서의 `폴더명 · 1`, `폴더명 · 2`로 구분되는지 확인합니다.
3. 대표 파일을 선택하고 `현재 로그 찾기`를 사용합니다. Windows는 `Ctrl+F`, macOS는 `⌘F`입니다. `@PASS`, `DIAG_FAIL`, `TEST_FAIL`, `TRAINING_FAIL`, `WATCHDOG_RESET`, `SYSTEM_REBOOT` 같은 실제 로그 문자열을 검색합니다.
4. 검색으로 확인한 줄의 왼쪽 `근거 거터`를 눌러 판정 근거를 지정합니다. 오른쪽 `원문 북마크`에 줄 번호와 원문 일부가 표시되는지 확인합니다.
5. 오른쪽 `결과`에서 `Pass`, `Diag fail`, `Test fail`, `Training fail`, `System halt`, `System reboot`, `Incomplete`, `Unknown` 중 하나를 선택합니다. 근거가 부족하면 `Unknown`을 선택하고 `검토 필요` 상태로 둡니다.
6. 같은 조건의 검색 기록을 모은 뒤 `분석 규칙 저장`을 누릅니다. `판정에 사용할 검색을 선택하세요`에서 필요한 검색을 선택하고, 순서가 필요하면 `표시된 순서대로 나타나야 함`을 켭니다.
7. `규칙 저장`을 누른 뒤 `전체에 미리 적용`을 누릅니다. 결과와 함께 표시되는 `예외 N개 확인`을 눌러 개별 파일을 확인합니다.
8. Run1과 Run2를 같은 `Sample|온도|Mode` 조합으로 비교합니다. `PASS → PASS`는 안정 통과, `비-PASS → PASS`는 회복, `PASS → 비-PASS`는 회귀로 기록하고, 그 외에는 해당 결과와 근거를 함께 남깁니다.

### 기대 결과

- 왼쪽 목록에 모든 `.log` 파일이 출처 폴더와 상대 경로별로 표시됩니다.
- `검색 결과`와 `예외 로그` 목록에서 누락 파일과 규칙 예외를 확인할 수 있습니다.
- 규칙 적용 결과는 후보로 제시되며, 엔지니어가 저장한 기존 판정은 충돌 시 유지됩니다.
- fixture의 48개 파일은 manifest의 결과 수량인 `PASS 23`, `DIAG_FAIL 3`, `TEST_FAIL 3`, `TRAINING_FAIL 3`, `SYSTEM_HALT 5`, `SYSTEM_REBOOT 4`, `INCOMPLETE 4`, `UNKNOWN 3`과 대조할 수 있습니다.

### 예외 처리

- 가져오기 알림에 `실패`, `제외`, `10,000개 제한 도달`이 있으면 원본 폴더의 확장자와 파일 경로를 확인한 뒤 누락 폴더를 별도로 `로그 폴더 열기`합니다.
- 정규식이 잘못되면 검색 상태가 `식 오류`가 됩니다. 검색식을 고친 뒤 다시 검색합니다. 검색 자체가 실패하면 `검색 실패` 메시지와 파일 상태를 기록합니다.
- `예외 N개 확인`에서 `일치하는 규칙 없음`, `동순위 규칙 충돌`, `판정 근거 누락`, `로그 검사 실패`가 보이면 해당 파일의 검색 결과와 `원문 북마크`를 다시 확인합니다.
- 파일 내용이 재수집 중 변경되면 새 파일 자료로 취급하고 이전 판정을 자동 적용하지 않습니다. 새 원문을 열어 다시 판정합니다.

## 2. Bring-up/Debug 엔지니어: UEFI에서 OS까지 정지·재부팅·Training 실패 추적

### 입력과 목표

`qualcomm-bringup` fixture의 `pass`, `uefi-failure`, `uefi-exit`, `os-failure`, `reboot-recovered`, `stale-conflict`, `multiple-runs` 폴더를 사용합니다. 합성 로그의 기본 단계는 `SYN_POWER_ON → SYN_UEFI_ENTER → SYN_UEFI_EXIT → SYN_OS_BOOT_START → SYN_OS_READY`입니다. 현재 UI의 결과 선택 항목은 `Pass`, `Diag fail`, `Test fail`, `Training fail`, `System halt`, `System reboot`, `Incomplete`, `Unknown`, `Excluded`입니다. fixture manifest의 `UEFI_FAIL`, `UEFI_EXIT_FAIL`, `OS_PANIC`은 검증용 oracle 이름이므로 화면의 결과 항목으로 직접 선택하지 않습니다.

### 작업 순서

1. `로그 폴더 열기`로 대상 fixture 폴더를 등록합니다. 폴더와 파일 수, `relative_path`에 해당하는 파일명을 확인합니다.
2. `전체 로그 찾기`를 누릅니다. Windows는 `Ctrl+Shift+F`, macOS는 `⌘⇧F`입니다. `UEFI entry`, `ExitBootServices`, `OS boot start`, `HIDAG START`, `TRAINING_FAIL`, `WATCHDOG_RESET`, `SYSTEM_REBOOT`를 차례로 검색합니다.
3. 왼쪽 `검색 결과` 행을 눌러 파일과 줄 위치를 엽니다. 확인할 파일을 여러 개 선택하면 가운데 `열린 탭`에 추가됩니다.
4. 열린 파일만 비교할 때 `열린 탭 찾기`를 누릅니다. Windows는 `Ctrl+Alt+F`, macOS는 `⌘⌥F`입니다. 현재 한 파일만 확인할 때는 `현재 로그 찾기`를 사용합니다.
5. 각 파일에서 다음 순서와 종료 상태를 확인합니다.

   - `UEFI entry` 뒤에 `ExitBootServices status=success`가 있는지 확인합니다.
   - `OS boot start` 뒤에 `HIDAG START` 또는 training 단계가 있는지 확인합니다.
   - `TRAINING_FAIL`가 있으면 `Training fail`을 선택합니다.
   - `WATCHDOG_RESET`와 `SYSTEM_REBOOT`가 순서대로 있으면 `System reboot`를 선택합니다.
   - terminal 결과 없이 `console_state=halted`가 있으면 `System halt`를 선택합니다.
   - 종료 단계가 없거나 캡처가 모호하면 `Incomplete` 또는 `Unknown`을 선택하고 `검토 필요`로 둡니다.

6. 판정에 사용할 UEFI, OS, 실패, 재부팅 줄의 `근거 거터`를 눌러 `원문 북마크`를 만듭니다. `Ln N` 항목을 누르면 해당 줄로 이동합니다.
7. 파일의 기존 판정과 새 후보가 다르면 `기존 PASS → SYSTEM_HALT 변경 확정`과 같은 형식의 변경 버튼을 확인합니다. 원문 근거를 확인한 뒤에만 변경을 확정합니다.

### 기대 결과

- `검색 결과`에서 UEFI, OS, training, watchdog 줄을 파일별로 찾을 수 있습니다.
- `열린 탭` 검색은 현재 열린 파일 집합만 검색하며, 닫은 파일 결과는 포함하지 않습니다.
- 각 파일의 `원문 북마크`에 확인한 줄 번호가 남고, `결과`와 `판정 검토`가 함께 표시됩니다.
- 재부팅 후 회복된 fixture는 첫 실행의 `System reboot`와 다음 실행의 `Pass`를 별도 파일로 확인할 수 있습니다.

### 예외 처리

- `검색 결과`가 80개를 초과하면 `상위 80개 표시 · 전체 N개`를 확인하고 검색어를 단계별로 좁힙니다.
- 검색 결과가 없으면 입력한 문자열, `검색 범위`, `대/소문자 구분`, `단어 단위 일치`, `정규식 사용` 설정을 확인합니다.
- 파일을 닫으면 해당 탭의 원문 구간과 북마크 캐시가 제거됩니다. 다시 검토할 때 파일 행을 눌러 탭을 다시 엽니다.
- `UEFI entry`만 있고 다음 단계가 없거나 종료 marker가 없으면 `System halt`를 임의로 확정하지 않습니다. 캡처 상태를 확인할 수 없으면 `Unknown` 또는 `Incomplete`을 선택합니다.
- AI 결과나 fixture oracle만으로 결과를 확정하지 않습니다. 줄 근거를 확인한 뒤 엔지니어 판정을 저장합니다.

## 3. 리포트 오너: 행·열·근거를 선택해 CSV/TSV 만들기

### 입력과 목표

`결과표`에서 전달할 파일 집합과 열을 정합니다. 보고서에 포함할 상태, 폴더, 파일, 메타데이터, 결과, 검토 상태, 근거 수를 확인한 뒤 CSV 파일 또는 TSV 클립보드를 만듭니다.

### 작업 순서

1. `결과표`를 엽니다. 검색 입력에 `파일명, 폴더, 조건 검색`을 입력합니다.
2. `결과`에서 `Pass`, `Diag fail`, `Test fail`, `Training fail`, `System halt`, `System reboot`, `Incomplete`, `Unknown`, `Excluded` 중 필요한 값을 선택합니다.
3. `검토`에서 `검토 필요` 또는 `확정`을 선택하고, 필요하면 `폴더 범위`에서 특정 폴더를 선택합니다. 조건을 다시 시작하려면 `초기화`를 누릅니다.
4. 행 왼쪽 체크 상자를 선택합니다. `필터된 행 전체 선택`을 사용하면 현재 필터 결과 전체를 선택합니다. 선택한 행이 있으면 현재 필터·폴더 범위 안에 남아 있는 선택 행만 내보내고, 숨겨진 선택은 다음 범위를 위해 유지합니다. 선택한 행이 없으면 현재 필터·폴더 범위 전체를 내보냅니다.
5. `열 선택`을 눌러 `내보낼 열`을 엽니다. 기본은 메타데이터·결과 16개 열이며, `근거` 묶음은 명시적으로 켰을 때만 `근거 수`와 `선택 근거 수`를 함께 추가합니다. 개별 기본 열에는 `Source ID`, `Artifact ID`, `Source key`, `Relative path`, `Run`, `파일명`, `폴더`, `Sample 값`, `Sample 상태`, `온도 값`, `온도 상태`, `Mode 값`, `Mode 상태`, `결과`, `결과 출처`, `검토`가 있습니다.
6. 파일로 전달할 때 `CSV`를 누릅니다. 표의 현재 필터와 선택 열이 반영된 날짜 형식 파일이 생성됩니다.
7. 표 계산기에 바로 붙여 넣을 때 `TSV 복사`를 누릅니다. 복사된 헤더와 행을 대상 문서의 시작 셀에 붙여 넣고 행 수와 열 순서를 확인합니다.

### 기대 결과

- 선택 행이 없으면 화면의 필터 결과 수와, 선택 행이 있으면 현재 범위 안 선택 행 수와 내보낸 행 수가 일치합니다.
- `결과`, `검토`, `폴더 범위`, 정렬된 열의 순서가 내보내기에 반영됩니다.
- `근거 수`와 `선택 근거 수`는 `근거` 그룹을 켰을 때만 내보내며, 각각 현재 결과 근거 수와 엔지니어가 선택한 근거 수를 표시합니다.
- CSV와 TSV의 헤더는 선택한 열의 순서를 따르며, `relative_path`, `Source ID`, `Artifact ID`로 같은 파일명을 구분할 수 있습니다.

### 예외 처리

- 결과가 0행이면 `TSV 복사`와 `CSV`가 비활성화됩니다. 검색어와 `결과`, `검토`, `폴더 범위`를 확인하고 `초기화`를 사용합니다.
- `검토 필요` 행은 `로그` 화면에서 파일을 열어 `원문 북마크`, `결과`, 근거 줄을 확인한 뒤 내보냅니다.
- `Sample`, `온도`, `Mode`가 `후보`이면 원문과 파일명을 확인하고 후보 값을 누릅니다. `승인`, `거절`, `미확인` 상태를 보고서에 포함할지 결정합니다.
- `TSV 복사`에서 `클립보드에 복사하지 못했습니다.`가 표시되면 클립보드 권한을 확인한 뒤 다시 누릅니다.
- CSV나 TSV를 외부 도구에 전달하기 전에는 현재 폴더 범위, 행 선택 교집합, 행 수, 선택 열, `검토` 값을 다시 확인합니다. 근거 그룹을 켠 경우에만 두 근거 열도 확인합니다. 원본 로그 파일은 내보내기 과정에서 변경되지 않습니다.

## 선택 사항: OpenAI-compatible vLLM 지연 응답과 AI 패턴 검토

AI 기능은 선택한 로그의 패턴을 검토하는 보조 작업입니다. 판정과 규칙 저장은 엔지니어가 수행합니다.

1. `설정` 화면의 `LLM 연결`에서 vLLM의 OpenAI-compatible `/v1` 주소를 `Base URL`에 입력합니다. `Model`에 모델 ID를 입력하고 필요하면 `API key`를 입력합니다.
2. `모델 목록 확인`을 눌러 연결과 모델을 확인합니다. 응답이 느리면 `연결 중` 상태를 기다리고, 확인에 실패하면 Base URL, 모델 ID, 네트워크를 점검합니다.
3. `호출 제한`의 `RPM`, `TPM`, `Timeout`, `Retries`를 vLLM 운영값에 맞춰 입력하고 `저장`을 누릅니다. 현재 기본값은 RPM `8`, TPM `80,000`, Timeout `60`초, Retries `2`입니다.
4. `로그`에서 파일을 선택하고 필요하면 `검토 메모 (선택)`을 입력한 뒤 `검토 실행`을 누릅니다. 대기 중에는 `분석 요청 중…`, `대기 N번`, `사내 LLM 응답 대기`, `LLM 사용량 대기 · 약 N초`, `LLM 재시도 N/M`, `검토 중` 상태가 표시될 수 있습니다.
5. 결과가 나오면 `검토 결과`, `추천 태그·검색`, 경고를 확인합니다. 추천 검색은 필요한 경우 현재 로그 검색에 사용하고, 줄 근거와 결과 선택을 직접 확인합니다.
6. 대기가 너무 길거나 작업을 중단할 때는 `취소`를 누릅니다. LLM이 느리거나 제한되어도 로컬의 로그 검색, 정규식, 판정 규칙, 결과표, 패턴 집계는 계속 사용할 수 있습니다.

AI 패턴 검토 결과를 확인한 뒤 판정과 규칙 저장은 기존 Workbench 동작에서 직접 수행합니다.
