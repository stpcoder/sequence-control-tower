# 로그 분석과 규칙

## 검색과 근거

검색은 탐색과 판정에 함께 사용됩니다. 검색 결과의 개수, 파일 범위, 문자열 또는 정규식 여부, 대소문자 조건이 프로젝트에 기록됩니다. 선택한 원문 줄은 `근거 거터`에서 다시 열 수 있고 `원문 북마크`로 보관할 수 있습니다.

검색 기록만으로 판정 규칙이 생기지는 않습니다. 단순 탐색을 잘못 학습하는 것을 막기 위한 구분입니다.

## 규칙 만들기

`규칙`에서 다음 조건을 조합합니다.

- marker가 0개인지, 1개 이상인지, 정확히 N개인지
- marker가 반드시 있어야 하는지 없어야 하는지
- 여러 marker가 어떤 순서로 나와야 하는지
- 문자열, 정규식, 대소문자, 본문 또는 파일명 범위
- 규칙이 확정하는 결과 상태

저장한 규칙은 프로젝트 revision으로 보관됩니다. 전체 적용 결과는 확정 전에 미리 검토할 수 있으며, 충돌·근거 누락·검색 실패 로그는 예외로 분리됩니다.

## Agent가 엔지니어의 분석 순서를 배우는 과정

1. 엔지니어가 `Ctrl+F` 또는 전체 검색으로 실제 확인 작업을 수행합니다.
2. 앱은 최근 검색어, 순서, 검색 범위, 일치 개수와 현재 파일을 기록합니다.
3. 엔지니어가 현재 평가 결과를 확정하면 최근 8시간 안의 검색 중 마지막 20개를 후보로 보여줍니다.
4. 두 개 이상의 서로 다른 검색이 있을 때만 `이번 분석` 확인이 나타납니다.
5. 단순 탐색 검색은 체크를 해제하고, 실제 판정에 사용한 검색은 위·아래 버튼으로 순서를 맞춥니다.
6. Agent가 “어떤 목적의 확인이었는지” 한 번 묻습니다.
7. 엔지니어가 목적을 저장하면 선택한 marker의 있음·없음, 검색 순서, 단계와 결과만 프로젝트 분석 절차로 확정됩니다.
8. 다음 로그에서 동일 절차가 다시 나타나면 `engineer_workflow_apply`가 후보 판정과 근거를 보여줍니다.

같은 검색을 10초 안에 반복한 기록은 중복 저장하지 않습니다. 건너뛴 후보는 학습에 사용하지 않습니다. 저장된 절차가 달라졌을 때 Agent가 조용히 덮어쓰지 않고 다시 확인합니다.

## 결과 Export 구성 저장

`결과`의 `열 선택`에서 CSV·TSV에 포함할 열을 고릅니다. `프로젝트 기본값 저장`을 누르면 열과 순서가 현재 프로젝트에 저장됩니다. 프로젝트를 다시 열어도 같은 구성이 복원되고, 새 프로젝트에서 기존 설정을 재사용하면 이 Export 구성도 함께 복사됩니다.

## 콘솔 입력과 장비 출력 구분

`console_transcript_scan`은 UEFI, LK, OS shell 같은 prompt 뒤의 문자열을 엔지니어 입력 명령 후보로 분리합니다. `sleep 20`, test command, mode 설정과 같은 입력만 명령 지식에 저장합니다.

`@PASS`, `@FAIL`, training fail, watchdog, reboot, halt는 장비 출력이지만 판정 근거로 유지합니다. 처음 보는 prompt는 다음 중 한 가지로 확인합니다.

- 입력 명령으로 기억
- 이번 줄만 입력
- 장비 출력으로 제외
- 건너뛰기

처음 보는 명령의 목적도 필요한 경우 한 번 묻고, 프로젝트·SoC·부팅 profile 범위의 명령 지식으로 저장합니다.

## 결정적 Pass/Fail 판정

로컬 상태기계는 LLM보다 먼저 marker 우선순위를 적용합니다.

1. training fail
2. `@FAIL` 또는 fast fail
3. reboot 또는 watchdog
4. halt 또는 fatal
5. `@PASS`
6. 진단 시작 후 종료 marker 없음: system halt 후보
7. stress pass와 정상 종료: pass
8. 나머지: incomplete

LLM은 이 수치를 다시 계산하지 않고, 조건과 이력을 연결해 설명합니다.
