# 문제 해결

이 문서는 Log Workbench의 현재 오류 처리와 확인 절차를 정리합니다. 각 항목은 `문제 → 확인 → 조치` 순서로 기록합니다.

이 문서에서 `N`은 화면에 표시되는 실제 개수·초·재시도 번호를 대신하는 숫자입니다. `Ln N`은 원문 창의 N번째 줄 위치를 뜻하며, 예를 들어 `Ln 42`는 42번째 줄입니다.

## 로그 폴더 가져오기

### 1. 폴더 가져오기가 10,000개에서 멈춤

**문제**

알림에 `10,000개 로그를 불러왔지만 일부는 처리하지 못했습니다 · 10,000개 제한 도달.`이 표시됩니다.

**확인**

1. `로그`에서 폴더 그룹별 파일 수를 확인합니다.
2. 알림의 `실패 N`, `제외 N`, `10,000개 제한 도달`을 확인합니다.
3. 원본 폴더에서 확장자가 `.log`인 파일 수를 확인합니다. 하위 폴더의 `.log`도 포함합니다.

**조치**

1. 폴더를 여러 작업 단위로 나눕니다.
2. 각 폴더를 `로그 폴더 열기`로 등록합니다.
3. 새로 등록한 폴더 그룹의 파일 수를 확인합니다.
4. 제한에 걸린 작업의 결과 집계를 시작하지 않습니다.

가져오기 상한은 10,000개입니다. 상한 도달은 `실패` 항목으로 기록되지 않으며 알림의 `10,000개 제한 도달`로 확인합니다.

### 2. 같은 폴더 또는 중복·겹치는 폴더를 여러 번 선택함

**문제**

같은 경로, 대소문자만 다른 경로(Windows), 상위 폴더와 하위 폴더를 함께 선택했습니다. 동일 파일이 반복 등록되거나 제한 수가 예상보다 빨리 줄어들 수 있습니다.

**확인**

1. 선택한 폴더 목록에서 같은 경로를 제거합니다.
2. 상위 폴더와 그 하위 폴더를 동시에 선택했는지 확인합니다.
3. `로그`의 폴더 그룹과 파일 수를 확인합니다.
4. 동일 내용 파일의 출처가 필요한 경우 각 행의 폴더와 상대 경로를 확인합니다. 같은 폴더 라벨의 가져온 루트는 결과표에서 안정적인 root ID 순서에 따라 `폴더명 · 1`, `폴더명 · 2`로 분리됩니다.

**조치**

1. 같은 경로는 한 번만 선택합니다.
2. 상위 폴더를 선택했다면 하위 폴더를 별도로 선택하지 않습니다.
3. 다시 가져온 뒤 파일별 `상대 경로`와 폴더 그룹의 개수를 비교합니다.

가져오기는 canonical path 기준으로 같은 루트와 상·하위 루트를 정리한 뒤 파일을 한 번만 탐색합니다. 동일 내용 파일은 SHA 기준으로 하나의 원문 저장 대상을 공유하고, 서로 다른 원본은 별도 출처 행으로 유지합니다.

### 3. 심볼릭 링크 폴더가 거부됨

**문제**

선택한 루트가 심볼릭 링크이면 실패 이유가 `심볼릭 링크 폴더는 가져올 수 없습니다.`로 기록됩니다. 폴더 내부의 심볼릭 링크 디렉터리와 파일은 제외 수에 포함됩니다.

**확인**

1. 선택한 폴더의 파일 시스템 종류를 확인합니다.
2. 알림에 `실패 1` 또는 `제외 N`이 표시되는지 확인합니다.
3. 원본 폴더 안에 심볼릭 링크 항목이 있는지 확인합니다.

**조치**

1. 심볼릭 링크가 가리키는 실제 디렉터리를 선택합니다.
2. 내부 심볼릭 링크 항목은 실제 파일을 별도 디렉터리로 복사한 뒤 다시 가져옵니다.
3. 가져온 로그 수와 `제외 N`을 다시 확인합니다.

선택한 루트가 디렉터리가 아니면 `폴더만 가져올 수 있습니다.`가 표시됩니다.

## 검색과 원문 열기

### 4. 검색 결과가 이전 검색어로 남거나 새 검색 중 결과가 바뀜

**문제**

검색어를 빠르게 바꾼 뒤 이전 검색의 결과가 늦게 도착하거나, 화면에 `로컬 로그 검색 중…`이 오래 표시됩니다.

**확인**

1. 검색창의 현재 검색어를 확인합니다.
2. 검색 범위가 `현재 로그 찾기`인지 `전체 로그 찾기`인지 확인합니다.
3. 검색 옵션 `대/소문자 구분`, `단어 단위 일치`, `정규식 사용`을 확인합니다.
4. 검색 결과 목록의 파일명과 줄 번호가 현재 검색어와 일치하는지 확인합니다.

**조치**

1. 검색창의 현재 내용을 지운 뒤 검색어를 다시 입력합니다.
2. `Enter` 또는 `F3`으로 다음 결과를 이동합니다. 이전 결과는 `Shift+Enter` 또는 `Shift+F3`을 사용합니다.
3. 이전 검색 결과가 새 검색 결과에 섞였으면 `검색 닫기` 후 `현재 로그 찾기` 또는 `전체 로그 찾기`를 다시 선택합니다.
4. 검색 오류가 표시되면 결과를 판정 근거로 저장하지 않고 오류 문구를 확인합니다.

새 검색 요청이 시작되면 이전 검색 요청은 취소되며, 이전 요청의 결과는 현재 화면에 적용되지 않습니다. 검색 취소 자체를 별도 성공 알림으로 표시하지 않습니다.

### 5. 검색을 취소했는데 `검색 실패`가 표시됨

**문제**

검색어를 바꾸거나 화면을 이동한 직후 `검색 실패` 또는 `검색하지 못했습니다.`가 표시됩니다.

**확인**

1. 검색어를 바꾼 직후 발생했는지 확인합니다.
2. `검색 중` 표시가 사라졌는지 확인합니다.
3. 새 검색어로 검색 결과 수와 파일별 오류를 확인합니다.

**조치**

1. 현재 검색어를 그대로 한 번 더 입력합니다.
2. 검색 결과가 정상 표시되면 이전 요청의 취소로 처리하고 현재 결과만 사용합니다.
3. 같은 파일에서 반복되면 파일별 오류 문구를 확인하고 원문을 다시 엽니다.
4. 검색이 끝나지 않으면 `검색 닫기` 후 앱의 `로그` 화면에서 다시 검색합니다.

판정 규칙의 부재 조건에는 파일별 검색 오류를 사용하지 않습니다. 검색이 성공한 파일에서 확인한 일치 수만 규칙 근거로 사용합니다.

### 6. 긴 한 줄 때문에 검색 실패

**문제**

검색 결과의 파일 오류에 `한 줄이 4 MB를 초과해 안전하게 검색할 수 없습니다.`가 표시됩니다.

**확인**

1. 오류가 표시된 파일을 확인합니다.
2. 원본 파일에서 개행 없이 4 MB를 초과하는 줄이 있는지 확인합니다.
3. 같은 검색어를 다른 로그에서 실행해 검색식 자체의 오류인지 구분합니다.

**조치**

1. 원본 수집 도구에서 긴 줄을 개행 단위로 분할해 새 로그를 생성합니다.
2. 수정된 파일을 별도 경로에 저장하고 `로그 폴더 열기`로 다시 가져옵니다.
3. 새 파일에서 검색을 다시 실행합니다.
4. 기존 파일의 검색 결과를 `0회` 근거로 저장하지 않습니다.

### 7. 이진 파일 또는 NUL 문자가 포함된 로그

**문제**

원문 열기 또는 검색에서 `이진 파일은 텍스트로 검색할 수 없습니다.` 또는 `이진 파일은 텍스트로 열 수 없습니다.`가 표시됩니다.

**확인**

1. `로그` 목록에서 해당 파일을 선택하고 `원문 열기`를 누릅니다. `이진 파일은 텍스트로 열 수 없습니다.`가 표시되는지 확인합니다.
2. 같은 파일에서 `현재 로그 찾기`를 열고 `@PASS`, `@FAIL`, `stressapp` 중 하나를 검색합니다. `이진 파일은 텍스트로 검색할 수 없습니다.`가 표시되는지 확인합니다.
3. `전체 로그 찾기`에서 해당 파일의 오류와 검색 결과 수를 확인합니다. 앱이 파일을 읽지 못한 상태이면 검색 결과를 판정 근거로 사용하지 않습니다.

**조치**

1. 원본 파일을 별도 작업 폴더에 복사한 뒤 복사본만 텍스트 변환 대상으로 사용합니다. 앱에 등록된 원본 파일은 그대로 보존합니다.
2. 복사본의 변환 규칙(인코딩, 개행, NUL 처리)과 변환으로 제외된 바이트 또는 줄을 기록합니다.
3. 변환된 파일을 새 폴더에 저장하고 `로그 폴더 열기`로 다시 가져옵니다. `로그`에서 원문을 열고 `@PASS`, `@FAIL`, `stressapp` 검색 결과를 확인합니다.
4. 원문을 읽지 못한 파일에는 PASS, FAIL, 부재 조건을 저장하지 않습니다.

## 판정 상태

### 8. 로그 끝이 잘렸거나 완료 근거가 없음

**문제**

로그 끝부분에 `normal_end: true` 또는 전체 실행 결과 줄이 없거나 필요한 실행 구간이 확인되지 않습니다. 결과표에 `Incomplete` 또는 `Unknown`이 표시되거나 `검토 필요`가 유지됩니다.

**확인**

1. `@PASS DIAG_COMPLETE`, `@FAIL code=DG_021`, `normal_end: true`, `SYSTEM_REBOOT reason=watchdog`를 각각 검색합니다.
2. `stressapp: start`, `hidag: start`, `training: start`와 각 줄의 timestamp를 확인합니다.
3. 파일 수집 도구에서 수집 종료 상태와 파일 크기를 확인합니다.
4. 현재 실행의 시작 줄부터 파일 끝까지 위 문자열의 순서와 timestamp가 이어지는지 확인합니다. 이전 실행의 `@PASS` 또는 `@FAIL`이 현재 실행 앞부분에 있으면 현재 실행의 결과 근거로 사용하지 않습니다.

**조치**

1. `stressapp: start`와 `hidag: start` 뒤에 파일이 끝나고 `@PASS DIAG_COMPLETE`, `@FAIL code=DG_021`, `normal_end: true`가 모두 없으면 `결과`에서 `Incomplete`를 선택합니다.
2. 같은 실행 구간에 `@PASS DIAG_COMPLETE`와 `@FAIL code=DG_021`이 함께 있거나, 실행 구간을 나눌 수 없으면 `Unknown`을 선택합니다.
3. 확인한 줄 왼쪽을 눌러 `원문 북마크`를 지정합니다.
4. 근거가 부족한 상태에서 `Pass`, `Diag fail`, `Test fail`, `System halt`를 확정하지 않습니다.

예시 규칙으로 `@PASS DIAG_COMPLETE`와 `normal_end: true`가 같은 실행 구간에 있고 `@FAIL code=DG_021`, `SYSTEM_REBOOT reason=watchdog`가 없으면 `Pass` 판정 근거로 사용할 수 있습니다. `@FAIL code=DG_021`이 `hidag: start` 뒤에 있으면 `Diag fail`, `SYSTEM_REBOOT reason=watchdog`가 있으면 `System reboot` 조건으로 기록합니다. `Unknown`은 결과표의 `result` 열에 `UNKNOWN`으로 기록되며 `검토 필요` 상태를 유지합니다.

### 9. 결과표의 화면 행 수와 CSV/TSV 행 수가 다름

**문제**

화면에 보이는 현재 페이지의 행 수와 내보낸 파일의 행 수가 다릅니다.

**확인**

1. `결과표` 상단의 `{필터 적용 행 수} / {전체 행 수} logs`를 확인합니다.
2. `결과`, `검토`, `폴더 범위`, `파일명, 폴더, 조건 검색` 필터를 확인합니다.
3. 페이지에 현재 보이는 행 수와 필터 적용 행 수를 구분합니다.
4. 행을 선택했다면 숨겨진 선택이 있는지 확인합니다. 내보내기는 현재 필터·폴더 범위 안의 선택 행만 사용합니다.

**조치**

1. 필요한 행만 남기도록 필터를 적용합니다.
2. 선택 행이 없으면 전체 필터 적용 행을, 선택 행이 있으면 현재 범위 안의 선택 행만 내보내려면 `CSV`를 누릅니다. 성공 알림은 `{N}개 행을 CSV로 내보냈습니다.`입니다.
3. Excel에 붙여넣을 때는 같은 범위 규칙으로 `TSV 복사`를 누릅니다. 성공 알림은 `{N}개 행을 TSV로 복사했습니다.`입니다.
4. 필터 없이 전체 행이 필요하면 `초기화`를 누른 뒤 상단의 행 수를 확인하고 다시 내보냅니다.
5. 전달 전 기본 CSV/TSV 첫 줄이 아래의 정확한 16개 헤더인지 확인합니다. `근거` 그룹을 켰다면 두 근거 열이 추가되며, 행 수는 현재 내보내기 범위와 일치해야 합니다.

   `source_id,artifact_id,source_key,relative_path,run,filename,folder,sample_value,sample_state,temperature_value,temperature_state,mode_value,mode_state,result,result_source,review`

CSV와 TSV는 현재 페이지의 행만 내보내지 않고 현재 필터·폴더 범위에 남은 행을 사용합니다. 선택 행이 있으면 그 범위와 선택의 교집합만 내보내며, 숨겨진 선택은 다음 필터에서 사용할 수 있도록 유지됩니다. 동일 내용의 여러 원본은 root-aware 폴더와 각 출처 식별자에 해당하는 별도 행으로 유지됩니다.

## LLM 연결

### 10. LLM 응답 시간 초과

**문제**

분석 상태에 `사내 LLM 응답 대기`가 오래 표시된 뒤 `분석 실패`가 표시됩니다. `설정`의 `Timeout`에 지정한 시간이 지나 응답을 받지 못한 상태입니다.

**확인**

1. `설정`에서 `LLM 연결`의 `Base URL`, `Model`, `API key` 상태를 확인합니다.
2. `Timeout` 값과 `Retries` 값을 확인합니다. 기본값은 각각 60초와 2회입니다.
3. `모델 목록 확인`을 눌러 `/models` 응답이 `N개 모델 확인 · Nms` 또는 `연결됨 · Nms`로 끝나는지 확인합니다.

**조치**

1. `모델 목록 확인`이 성공하는지 확인한 뒤 같은 `Base URL`과 `Model`로 분석을 다시 실행합니다.
2. `Timeout`을 5~300초 범위에서 조정하고 `저장`을 누릅니다.
3. 일시 오류이면 `Retries`를 0~5 범위에서 조정하고 `저장`을 누른 뒤 분석을 다시 요청합니다.
4. LLM 없이 진행할 때 `로그` 검색, 판정 규칙, `결과표`, `패턴`을 사용합니다.

### 11. LLM 429 응답

**문제**

분석 중 상태에 `LLM 사용량 대기 · 약 N초` 또는 `LLM 재시도 N/M`이 표시되고, 최종 실패 시 `분석 실패`와 `LLM_HTTP_429`가 표시됩니다. `LLM_HTTP_429`는 `/chat/completions`의 HTTP 429 응답입니다.

**확인**

1. `설정`의 `호출 제한`에서 `RPM`, `TPM`, `Retries`를 확인합니다.
2. `LLM 사용량 대기 · 약 N초`이면 앱의 로컬 RPM·TPM 대기이며, 표시된 초가 지난 뒤 요청이 진행되는지 확인합니다.
3. `LLM 재시도 N/M`이면 Gateway가 HTTP 429를 반환한 뒤의 재시도입니다. Gateway 응답의 `Retry-After`가 숫자 초 또는 HTTP 날짜인지 확인합니다. 앱은 이 값을 최대 60초까지 적용하며, 값이 없거나 해석되지 않으면 약 1초, 2초, 4초 순으로 최대 15초까지 기다립니다.
4. `모델 목록 확인`에서 `연결 확인 실패: LLM_MODELS_HTTP_429`가 표시되면 `/models`의 HTTP 429이며 재시도 없이 1회 실패로 처리됩니다.
5. 분석이 재시도 후 완료됐는지, 최종적으로 `분석 실패`와 `LLM_HTTP_429`로 끝났는지 확인합니다.

**조치**

1. `LLM 사용량 대기 · 약 N초`가 표시되는 동안 같은 분석을 다시 요청하지 않고, 표시된 대기 시간이 끝날 때까지 기다립니다.
2. 사내 Gateway 한도에 맞게 `RPM`과 `TPM`을 낮춰 `저장`합니다.
3. `Retry-After` 대기 시간이 지난 뒤에도 `LLM 재시도 N/M`이 반복되면 Gateway의 공유 사용량과 `Retries` 설정을 확인합니다.
4. 최종 실패 시 로컬 분석을 진행하고 `LLM_HTTP_429`를 운영 기록에 남깁니다.

429 응답은 설정된 재시도 횟수까지 재요청합니다. 401과 403은 자동 재시도 대상이 아닙니다.

### 12. LLM 401 또는 403 응답

**문제**

분석이 `분석 실패`로 끝나며 `LLM_HTTP_401`(HTTP 401) 또는 `LLM_HTTP_403`(HTTP 403)이 표시됩니다. `모델 목록 확인` 중에는 `연결 확인 실패: LLM_MODELS_HTTP_401` 또는 `연결 확인 실패: LLM_MODELS_HTTP_403`이 표시됩니다.

**확인**

1. `Base URL`의 host와 경로가 사내 Gateway 주소인지 확인합니다.
2. `Model` 값이 해당 Gateway에서 허용된 모델 ID인지 확인합니다.
3. `API key` 항목의 상태를 확인합니다. 같은 host의 저장된 키는 `설정됨`, host가 바뀐 상태는 `주소 변경 · key 재입력 필요`, 키가 없는 상태는 `선택 사항`으로 표시됩니다.
4. Gateway의 인증 기록에서 키 또는 토큰의 발급 시각, 만료 시각, 폐기 여부, 대상 host와 scope를 확인합니다. 앱 화면에는 토큰 만료 시각을 표시하지 않습니다.
5. HTTP 401과 403은 자동 재시도하지 않으므로 `LLM 재시도 N/M`과 대기 상태가 표시되지 않는지 확인합니다. `모델 목록 확인`의 401·403도 한 번의 `/models` 요청으로 끝납니다.
6. Gateway 권한에서 모델 호출 권한과 `/models` 조회 권한을 확인합니다.

**조치**

1. 만료·폐기됐거나 대상 host와 scope가 맞지 않는 키 또는 단기 토큰을 Gateway 정책에 따라 새로 발급합니다.
2. `설정`의 `API key`에 새 값을 입력하고 `저장`을 누릅니다. `Base URL` host를 바꾼 경우 `주소 변경 · key 재입력 필요`가 사라지는지 확인합니다.
3. `모델 목록 확인`을 눌러 `N개 모델 확인 · Nms` 또는 `연결됨 · Nms`가 표시되는지 확인합니다.
4. `/models` 권한은 있지만 모델 호출 권한이 없으면 해당 모델 권한을 요청한 뒤 실제 분석을 1회 실행합니다.

### 13. LLM 응답이 느림

**문제**

상태에 `사내 LLM 응답 대기`가 오래 표시되거나 `연결 중`이 오래 유지됩니다.

**확인**

1. `설정`에서 `모델 목록 확인`의 응답 시간과 결과를 확인합니다.
2. 분석 상태가 `LLM 사용량 대기 · 약 N초`인지 `사내 LLM 응답 대기`인지 구분합니다.
3. `Timeout`, `RPM`, `TPM`을 확인합니다.

**조치**

1. `LLM 사용량 대기 · 약 N초`이면 Gateway 한도 회복을 기다립니다.
2. `사내 LLM 응답 대기`이면 Gateway 상태와 모델 부하를 확인합니다.
3. 필요한 경우 `Timeout`을 늘리고 `Retries`를 조정한 뒤 `저장`합니다.
4. 즉시 작업해야 하면 `로그`의 로컬 검색과 판정 기능을 사용합니다.

`설정` 화면에는 `LLM이 느리거나 제한되어도 로그 분석은 계속됩니다.`가 표시됩니다. 로그 원문 검색과 판정 규칙은 LLM 응답을 기다리지 않습니다.

### 14. API key 또는 토큰이 만료됨

**문제**

Gateway가 만료된 인증 정보로 요청을 거부하고 401 또는 403을 반환합니다. 별도의 `토큰 만료` UI 문구는 제공하지 않습니다.

**확인**

1. `LLM_HTTP_401`, `LLM_HTTP_403`, `LLM_MODELS_HTTP_401`, `LLM_MODELS_HTTP_403` 중 표시된 코드를 확인합니다.
2. Gateway에서 키의 만료 시각, 폐기 여부, scope를 확인합니다.
3. `설정`의 `API key` 상태와 `Base URL` host를 확인합니다.

**조치**

1. 새 API key 또는 토큰을 발급받습니다.
2. `설정`의 `API key`에 새 값을 입력하고 `저장`을 누릅니다.
3. `모델 목록 확인`으로 새 인증 정보의 권한을 확인합니다.
4. 이전 Gateway host를 계속 사용할 때는 host에 맞는 새 키를 입력합니다.

Gateway 주소가 바뀌고 새 키를 입력하지 않으면 저장 성공 알림에 `Gateway 주소가 바뀌어 이전 host의 API key를 안전하게 해제했습니다.`가 표시됩니다.

## 앱 화면과 열린 탭

### 15. 메뉴를 이동한 뒤 원하는 화면으로 돌아가지 못함

**문제**

`로그`, `결과표`, `패턴`, `설정`을 이동한 뒤 앱을 다시 열면 이전 화면과 다릅니다.

**확인**

1. 주소의 `screen` 값이 `workbench`, `results`, `patterns`, `settings` 중 하나인지 확인합니다.
2. 왼쪽 메뉴에서 현재 활성화된 항목을 확인합니다.
3. `결과표` 또는 `패턴`에서 파일을 열었는지 확인합니다.

**조치**

1. 원하는 메뉴를 다시 선택합니다.
2. 결과표 행을 열려면 해당 파일명을 누릅니다. 앱은 `로그` 화면으로 이동합니다.
3. 원문 검색은 `로그`에서 `현재 로그 찾기` 또는 `전체 로그 찾기`를 선택합니다.
4. 앱을 다시 연 뒤 화면이 달라지면 주소의 `screen` 값을 확인하고 왼쪽 메뉴에서 화면을 선택합니다.

현재 화면은 주소의 `?screen=` 값으로 복원됩니다. 지원되는 값은 `workbench`, `results`, `patterns`, `settings`입니다.

### 16. 닫은 로그 탭을 다시 열 수 없음

**문제**

원문 상단 탭에서 `탭 닫기`를 누른 뒤 해당 탭을 찾을 수 없습니다. 앱을 다시 열거나 화면을 이동한 뒤 열린 탭 목록이 달라질 수 있습니다.

**확인**

1. 왼쪽 `로그` 목록에서 파일명과 폴더 그룹을 확인합니다.
2. 파일의 `상대 경로`가 같은 이름의 다른 파일과 일치하는지 확인합니다.
3. `결과표`에서 파일명과 폴더 행을 확인합니다.

**조치**

1. 왼쪽 `로그` 목록에서 파일을 다시 선택합니다.
2. `결과표` 또는 `패턴`에서 해당 행을 눌러 `로그` 화면으로 돌아갑니다.
3. 원문이 열리면 필요한 줄을 다시 찾고 `원문 북마크`를 다시 지정합니다.
4. 파일이 목록에 없으면 `로그 폴더 열기`로 원본 폴더를 다시 가져옵니다.

열린 탭 목록은 현재 `로그` 화면의 세션 상태입니다. 앱 재실행과 화면 전환 뒤 탭 목록은 보존되지 않을 수 있습니다. 로그, 판정, 규칙, 결과 저장 상태는 탭 목록과 별도로 관리됩니다.
